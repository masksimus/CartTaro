# «Карты Таро» — изолированный HTTPS-стенд

Этот каталог предназначен **только для тестового VK Mini Apps-пилота**. Его нельзя применять к рабочему сайту без отдельного приёмочного тестирования. Он не меняет `main`, URL действующего VK-приложения или хранилище прежних пользователей.

## Схема

- **Caddy** принимает HTTPS на отдельном домене, выдаёт только файлы `pilot/` и проксирует `/api/v1/*` в приватный Node-сервер.
- **Node 24** проверяет подпись запуска ВК и записывает прогресс в SQLite.
- **SQLite** размещена в отдельном постоянном Docker volume. `docker compose down` не удаляет базу, если не передавать `-v`.
- Защищённый ключ поступает только файлом `/run/secrets/vk_protected_key`. Ни Caddy, ни клиентская страница ключ не получают.
- HTTP access logs выключены в Caddy, Docker container logs отключены, чтобы подписанные `vk_*`-параметры случайно не попали в журналы. Доступно только `/health` без персональных данных.

## Что требуется для фактического HTTPS запуска

Отдельный Linux VPS/сервер с Docker Engine и Compose v2, отдельный поддомен **не на работающем VK-адресе**, DNS A/AAAA на этот сервер, доступ TCP 80/443 (для автоматического TLS) и UDP 443 по желанию. Также необходим настоящий защищённый ключ приложения ВК 54582199, но **не сообщайте его в чате и не храните в GitHub**.

Если невозможно выделить отдельный адрес разработки в настройках ВК, для UAT создайте отдельное тестовое VK-приложение. В таком случае **отдельно** замените ожидаемый app ID и его собственный защищённый ключ; не пытайтесь авторизовать другое приложение секретом 54582199. Никаких адресов и разрешений действующей версии менять не требуется.

## Установка вручную на тестовом сервере

1. Клонировать именно `feature/tarot-v2-staging`. Не выполнять merge в `main`.
2. Скопировать `deploy/.env.example` в `deploy/.env`. Вписать новый тестовый `PILOT_DOMAIN` и абсолютный `VK_SECRET_FILE`. Не оставлять `.invalid` или `example` в качестве реального адреса.
3. Создать закрытый файл ключа **за пределами каталога репозитория**. Важны права `600`, владелец `UID 1000` (непривилегированный пользователь Node в контейнере), каталог также должен быть доступен этому UID. Вставлять ключ через защищённый ввод, не через URL, командную строку с историей или Git.
4. Выполнить из корня репозитория:

       set -a
       . ./deploy/.env
       set +a
       node deploy/preflight.mjs
       docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet
       docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --build

5. Проверить `https://<ваш-тестовый-домен>/health` (должно вернуть `{"status":"ok"}`) и страницу по корню домена. **Защищённые действия не должны работать без настоящих подписанных VK launch-параметров.**
6. Проверку в реальном VK выполнить **только** через отдельный адрес разработки/тестовое приложение, не подменяя продакшен URL.

В контейнере Caddy автоматически получает TLS-сертификат при корректных DNS и доступных портах. DNS/сертификаты/серверные реквизиты заранее не созданы, поэтому **готового публичного адреса пока нет**.

## Резервное копирование и откат

Создавать SQLite-копию транзакционно, а не простым копированием файла с работающим WAL:

    docker compose --env-file deploy/.env -f deploy/compose.yaml exec -T backend node server/src/backup.mjs /data/taro-progress.sqlite /data/backups/backup-20261103.sqlite

Сохранить копию **в зашифрованное внехостовое хранилище**. Путь каждой копии должен быть уникальным; попытка перезаписать существующий архив блокируется. Проверять восстановление на отдельном тестовом стенде.

Остановить без удаления данных:

    docker compose --env-file deploy/.env -f deploy/compose.yaml down

**Никогда не использовать `down -v`**, пока не создана и не проверена резервная копия. Не поднимать сервис на рабочем домене VK-приложения.

## Ограничения безопасности перед настоящим релизом

- Текущий лимит запросов действует **на подтверждённого пользователя в памяти одного Node-процесса**. Он не заменяет защиту по IP на внешнем WAF/сетевом уровне, анти-DDoS и централизованный rate-limit.
- Параметры запуска, подписанные VK, действуют 15 минут; обновление браузерной страницы после очистки query-строки разлогинивает — открыть снова через ВК.
- Нет синхронизации старых VK Storage данных, никаких реальных платежей или проверок вознаграждаемой рекламы. Не переносить клиентские балансы в серверную экономику.
- Критический UAT: настоящая подпись, VK Bridge на Android, ошибки при нестабильном интернете, корректность TLS, DNS, права секретов, backup/restore, отсутствие access logs.
- Это приложение **не является приватным только по факту отдельного домена**. Страница может открываться извне, но действия без настоящей HMAC-подписи должны завершаться отказом.
- Используется CDN VK Bridge через `unpkg.com`; если он недоступен пользователям, пилот откажет в доступе, не будет имитировать вход. Перед релизом следует локально поставлять версионированный SDK с проверкой лицензии и целостности.
- Доступ в настоящем VK и размещение DNS/HTTPS **не проводились** в рамках одного лишь добавления исходников.

## Отладка

Секреты и сырые URL не логировать. Для диагностики смотрите `/health`, результат `docker compose ... ps` и системное состояние сервисов. Если TLS не активировался, проверить DNS/маршрутизацию/доступ TCP 80, 443 и доступность ACME, не включать сырые журналы запросов с подписью запуска ВК.
