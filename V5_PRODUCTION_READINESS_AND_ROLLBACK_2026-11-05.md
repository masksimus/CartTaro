## 2. Препятствия до публичного релиза

1. **Нет утверждения владельца на публичное переключение.** Нельзя менять публичный URL ВК, основную Production ветку Vercel или `main` до явного разрешения.
2. **Нет независимого публичного окружения.** Существующее Production Vercel сейчас обслуживает V4, а в Preview V5 действует allowlist. Для открытого доступа к V5 нужно отдельное Production окружение/проект и проверенное переключение.
3. **Подпись ВК:** Preview UAT V5 может делегировать подтверждение действующему V4 endpoint. Для конечного публичного V5 нужен штатный секрет `VK_PROTECTED_KEY` в защищённых серверных переменных его Production окружения, без временной зависимости от V4.
4. **Политики и лицензии:** проверить тексты пользовательского соглашения, политики обработки данных, уведомление о развлекательном назначении Таро и территориальную правомерность использования исторических изображений. Никаких реальных денег или обмена кристаллов.
5. **Устойчивость:** проверить лимиты/скорость запросов, мониторинг `/api/v2/health`, правила алертов и план действий при `401`, `403`, `503`, `429`.
6. **Восстановление:** безопасно проверить восстановление snapshot в новую ветку Neon с проверкой количества записей, не трогая основные базы, и предусмотреть независимый экспорт/хранение.
7. **Матрица телефонов:** протестировано на Android, но перед массовым запуском отдельно проверить несколько устройств и распространённые версии VK WebView.
8. **ВК модерация:** подтвердить актуальные требования VK Mini Apps, необходимые разрешения, корректность скриншотов и содержание перед обновлением URL.

## 3. Go/no-go перед релизом

**GO**, только если:
- в новом изолированном Production окружении `/api/v2/health` → `database=connected,ready=true`;
- `/api/v2/status` → `public_game` только при сознательном включении;
- без подписанного входа `GET /api/v2/progress` → `401`, чужому аккаунту не раскрываются данные;
- подписанный ВК Android login, 1/3 расклада, исторические JPG, одна награда и карта в сутки, повторное открытие и устойчивость к повторным запросам проверены **в production-like окружении**;
- мониторинг и ответственное лицо на случай отката готовы;
- свежий снимок/экспорт сделан и возможность восстановления проверена;
- публичное обновление письменно/явно подтверждено владельцем.

Иначе **NO-GO**, V4 остаётся рабочей.

## 4. План раскатки (только после разрешения)

1. Зафиксировать проверенный commit V5 и его CI run, сделать новый резервный снимок перед cutover.
2. Настроить отдельную рабочую базу, секрет VK и fail-closed серверные флаги в новом V5 Production окружении. **Не подключать `neondb` вместо `tarot_v5_game`.**
3. Развернуть с неизменным публичным URL приложения ВК до проверки (только разработческий или отдельный стейджинг URL).
4. Выполнить GO-набор тестов внутри VK WebView, проверить нулевые повторы наград и доступность страниц.
5. После явного разрешения поменять только согласованный URL публичного приложения ВК на проверенный V5 Production URL, убедиться в работоспособности из обычного аккаунта.
6. Сохранить рабочую V4 как подготовленный откат, не удалять код и базу V4.

## 5. План отката — сначала восстановление трафика, затем диагностика

**Откат приложения (без изменения базы):**
- Возвратить публичный URL VK Mini Apps на последний проверенный рабочий URL V4, если в VK был изменён адрес.
- Если меняли алиас Vercel — вернуть его на конкретный ранее READY деплой V4 (проверить ID/алиас по текущему `get_deployment`; не опираться на старую строку без повторной проверки).
- Временно выключить `TARO_V2_WRITES_ENABLED` в V5 окружении и redeploy, если есть дубли наград/неожиданные записи.
- Проверить VK launch, карточки, историю и 1/3 раскладов на V4. Не удалять user data V5.

**Откат базы (только отдельным согласованием):**
- Изолировать проблему, сделать свежий снимок текущего состояния для анализа.
- Восстанавливать `snap-bold-bar-bawttimk` **в новую Neon branch**, проверить данные, затем отдельно планировать переключение DB URL. Прямое восстановление поверх живой ветки может стереть прогресс после снимка и требует отдельного согласия.
- Перед восстановлением сравнить дни/количество начислений и оценить риск потери пользовательских записей. Не копировать тестовые начисления в V4.
- Не удалять snapshot или рабочие базы.

## 6. Что запрещено делать в рамках подготовки

- Запускать V5 для всех без нового разрешения пользователя.
- Выводить/копировать `VK_PROTECTED_KEY`, `DATABASE_URL`, `TARO_V5_DATABASE_URL`, персональные VK ID в логи, GitHub и чат.
- Снимать Preview allowlist для публичного запуска через незакрытый тестовый адрес.
- Делать SQL DROP/DELETE или принудительный restore поверх живой базы.
